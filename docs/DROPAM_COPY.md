# DROPAM_COPY.md
## The Language, Voice, and Microcopy Contract of Dropam

This document defines the **non-negotiable language system** of Dropam.

It governs:
- every word
- every label
- every sentence
- every absence of words

Any copy, microcopy, system message, or label that violates this document is incorrect, even if it "reads well".

If code works but the language breaks this contract, the feature must be revised or removed.

Dropam does not speak like software.
Dropam speaks like a **surface**.

---

## 0. ABSOLUTE LANGUAGE POSITIONING

Dropam does not explain.
Dropam does not persuade.
Dropam does not coach.
Dropam does not reassure excessively.

Dropam **states**.

Language exists only to:
- orient
- confirm
- enable

Nothing more.

---

## 1. CORE LANGUAGE PHILOSOPHY

### 1.1 Language Is Infrastructure

Words in Dropam are not content.
They are **structural cues**.

If a word draws attention to itself, it is wrong.

### 1.2 Fewer Words Is Always Better

If something can be understood without text:
- remove the text

If one word works:
- do not use two

If silence works:
- prefer silence

---

## 2. TONE (NON-NEGOTIABLE)

Dropam's tone is:

- calm
- neutral
- confident
- restrained
- adult
- unforced

It is never:
- friendly
- enthusiastic
- apologetic
- playful
- motivational
- instructional

Dropam never says:
- "Welcome"
- "Great job"
- "You're all set"
- "Let's get started"
- "Oops"
- "Uh oh"

---

## 3. GRAMMAR & STRUCTURE RULES

### 3.1 Sentence Case Only

All copy uses **sentence case**.

Correct:
- Drop your brief here
- Send to client
- In progress

Incorrect:
- Drop Your Brief Here
- SEND TO CLIENT
- In Progress

### 3.2 Period Usage

- No periods at the end of UI labels
- Periods allowed only in multi-sentence system messages (rare)

### 3.3 Punctuation Restraint

Forbidden:
- exclamation marks
- emojis
- ellipses
- excessive commas

Allowed:
- simple commas
- hyphens only when structurally necessary

---

## 4. WORDS THAT MUST NEVER APPEAR

These words are banned from the UI, copy, and system messages.

Never use:
- task
- ticket
- card
- board
- workflow
- project
- dashboard
- pipeline
- assign task
- productivity
- optimize
- manage
- performance
- efficiency

If a feature requires these words, the feature is wrong.

---

## 5. CANONICAL TERMINOLOGY (SINGLE SOURCE)

These words have **one meaning only**.

Use them exactly as defined.

- brief  
  A unit of work dropped by a client.

- file  
  A digital asset attached to a brief.

- folder  
  A container for organizing briefs or files.

- deliver  
  The act of making work available to the client.

- message  
  A written exchange tied to a brief.

- pod  
  A group of internal people responsible for a brand.

- brand  
  The client entity with a unique drop surface.

Never substitute synonyms.

---

## 6. ACTION LABEL RULES

Action labels must:
- be short
- be direct
- describe the result, not the process

Correct:
- Take brief
- Send to client
- Mark in progress
- Move to review
- Deliver

Incorrect:
- Assign this brief to yourself
- Notify the client
- Change status to in progress
- Proceed to review stage

---

## 7. EMPTY STATES & INSTRUCTIONS

### 7.1 Empty States Are Minimal

Empty states must:
- contain at most one sentence
- never explain features
- never motivate action

Correct:
Drop your brief here

Incorrect:
Start by uploading your files so our team can begin working on your project.

### 7.2 Instruction Hierarchy

If instruction is unavoidable:
1) one short sentence
2) no follow-up explanation
3) no help links

---

## 8. SYSTEM FEEDBACK & CONFIRMATION

### 8.1 Success Feedback

Success is assumed.

Do not say:
- "Success"
- "Done"
- "Completed successfully"

State change is the confirmation.

### 8.2 Errors (Rare and Quiet)

Errors must be:
- factual
- minimal
- non-apologetic

Correct:
Upload failed

Incorrect:
Sorry, something went wrong while trying to upload your file. Please try again.

If recovery is possible:
- attempt silently first
- only show error if recovery fails

---

## 9. CLIENT VS INTERNAL LANGUAGE

### 9.1 Client Language

Client-facing language must:
- be neutral
- avoid internal terms
- avoid hierarchy

Clients never see:
- pod
- admin
- internal
- role labels

### 9.2 Internal Language

Internal users may see:
- pod
- review
- deadline
- reassignment

Even internally:
- language stays restrained
- no "management speak"

---

## 10. STATUS LABELS (LOCKED)

Only these status labels are allowed:

- new
- in progress
- review
- delivered

No variants.
No synonyms.
No icons replacing text.

---

## 11. CONFIRMATION & DESTRUCTIVE ACTIONS

### 11.1 Default Rule

Avoid confirmations unless irreversible.

### 11.2 When Required

If confirmation is required:
- use one short sentence
- no warning icons
- no emotional language

Correct:
Delete this folder?

Incorrect:
Are you sure you want to permanently delete this folder? This action cannot be undone.

---

## 12. ADMIN LANGUAGE

Admin language must:
- avoid power signaling
- avoid control framing

Correct:
Assign pod lead

Incorrect:
Manage team permissions

Admin actions should feel procedural, not authoritative.

---

## 13. PLACEHOLDERS & MICRO LABELS

Placeholders must:
- describe expected input
- not instruct beyond that

Correct:
Access key

Incorrect:
Please enter the access key provided to you by your administrator.

---

## 14. WHAT DROPAM NEVER SAYS

Dropam never:
- thanks the user
- apologizes unless strictly necessary
- celebrates actions
- motivates productivity
- explains obvious things

If copy feels like:
- onboarding
- coaching
- reassurance

It does not belong.

---

## 15. CHANGE CONTROL (LANGUAGE)

Before introducing any new word or phrase, ask:

- Is this necessary?
- Is it neutral?
- Is it shorter?
- Does silence work better?

If the answer to any is no, do not add it.

---

## 16. FINAL AUTHORITY

This document is final.

If:
- copy sounds good but violates this document
- copy improves clarity but increases verbosity
- copy feels friendly but breaks restraint

The copy is wrong.

Dropam does not speak loudly.
Dropam speaks precisely.
